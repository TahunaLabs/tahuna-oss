# Prompt

## General Guardrails (Mandatory)

1. Delivery discipline
- Execute in agreed order. No jumping.
- One issue = one commit.
- For every real change, log to Linear: issue, recommendation, commit hash, validation commands.
- Validate before commit: `bun run lint` (must include ESLint + TypeScript unused checks).
- If blocked or ambiguous, pause and clarify before touching unrelated code.

## Convex Guardrails (Mandatory)

Use these rules for any Convex backend change.

1. Scope and compatibility
- Never modify `web/convex/auth.ts` (official better-auth/convex tutorial copy).
- Before calling anything unused, check both `web/` and `cli/` (Go CLI consumes backend routes).
- Ignore `web/convex/_generated/` files when reviewing dead code (autogenerated).

2. Dead code and redundancy checks
- Remove unused code only after cross-checking call sites in web + CLI.
- Keep one canonical implementation. Delete duplicate/legacy paths.
- No backward compatibility for MVP unless explicitly requested.

3. Convex anti-pattern prevention
- No heavy fanout or object-store work in `query`; move to `action`.
- Avoid N+1 lookups; batch/fanout with limits.
- No silent caps on lists. Return explicit pagination/truncation metadata.

4. Consistency rules
- Preserve project discipline: same structure, naming, imports, and error style as surrounding code.
- Prefer absolute imports in Convex modules (`@convex/*`, `@/*`), enforced by ESLint.
- Keep DTO naming consistent across modules (single canonical keys, e.g. `environment_id`).
- No ad-hoc logging patterns.
- Keep error contracts consistent (`detail` / structured errors only).
