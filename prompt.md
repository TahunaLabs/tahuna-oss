# Prompt

## General Guardrails (Mandatory)

1. Delivery discipline
- Execute fixes in agreed order; do not jump ahead.
- One issue = one commit.
- Log every real code change to Linear with: issue, recommended fix, commit hash, validation commands.
- Validate with TypeScript (`bunx tsc --noEmit` and `--noUnusedLocals --noUnusedParameters`) before commit.

## Convex Guardrails (Mandatory)

Use these rules for any Convex backend change.

1. Scope and compatibility
- Never modify `web/convex/auth.ts` (official better-auth/convex tutorial copy).
- Before marking any Convex function/route as unused, search both `web/` and `cli/` (Go CLI consumes several HTTP routes).
- Ignore `web/convex/_generated/` files when reviewing dead code (autogenerated).

2. Dead code and redundancy checks
- Remove truly unused functions/imports/variables only after cross-checking call sites in web + CLI.
- Prefer one canonical implementation; remove legacy/fallback branches once migration is verified.
- Do not add backward-compatibility shims/fallbacks for MVP unless explicitly requested.

3. Convex anti-pattern prevention
- Do not put heavy fanout/object-store work in `query` handlers; move heavy paths to `action`.
- Avoid N+1 metadata lookups; batch and constrain fanout.
- Expose continuation semantics for capped lists: return explicit `has_more`, `next_cursor`, and truncation flags (no silent caps).

4. Consistency rules
- Preserve existing project code discipline: same structure/style/error-handling patterns as surrounding modules.
- Standardize response DTO naming across modules (use one key, e.g. `environment_id`).
- Avoid ad-hoc `console.*` logging patterns unless explicitly part of agreed observability design.
- Keep error contracts consistent (structured `detail`/ConvexError style, no mixed ad-hoc patterns).
